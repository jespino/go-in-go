# hashicorp/go-plugin's examples, with go-in-go

These are the five examples of
[hashicorp/go-plugin](https://github.com/hashicorp/go-plugin/tree/main/examples),
rebuilt with go-in-go. Each one does the same job as the original, with the
same commands, environment variables and output where possible.

The difference is the approach. In go-plugin, a plugin is a separate
executable: the host starts it as a subprocess and talks to it over net/rpc
or gRPC. In go-in-go, a plugin is a module file (`.gig`) that the host loads
into its own process and calls directly. A module has its own Go runtime and
heap, so it doesn't matter which Go version built the host.

Run them all, with their output checked, from the repository root:

```sh
make goplugin
```

## The examples

| go-plugin | here | What it shows |
|---|---|---|
| [basic](https://github.com/hashicorp/go-plugin/tree/main/examples/basic) | [`basic/`](basic/) | load a plugin and call it; the plugin's structured logs go to the host's logger |
| [grpc](https://github.com/hashicorp/go-plugin/tree/main/examples/grpc) | [`kv/`](kv/) | a key/value CLI whose storage is a plugin chosen at run time, with two interchangeable implementations |
| [bidirectional](https://github.com/hashicorp/go-plugin/tree/main/examples/bidirectional) | [`bidirectional/`](bidirectional/) | the plugin calls back into the host, which adds the numbers |
| [negotiated](https://github.com/hashicorp/go-plugin/tree/main/examples/negotiated) | [`negotiated/`](negotiated/) | one plugin implements protocol versions 2 and 3, and the host and the plugin agree on one |
| [streaming](https://github.com/hashicorp/go-plugin/tree/main/examples/streaming) | [`streaming/`](streaming/) | data streamed in chunks in both directions |

Each example has the layout of the original: the host in `main.go`, the
plugin in `plugin*/` (a module project with its own `go.mod`), and
`shared/`, the code both sides agree on. Here `shared/` is the bindings that
`go-in-go bindgen` generated from the plugin. [`hostfs/`](hostfs/) is the
file access the hosts give their plugins.

## From go-plugin to go-in-go

| go-plugin | go-in-go |
|---|---|
| plugin executable, `plugin.Serve` | module file built by `go-in-go build`; a `main` package with `//gig:export` functions |
| `plugin.NewClient` + `Client()` + `Dispense` | `shared.Load(path, imports, opts)` |
| `client.Kill()` | `m.Close()`: unmaps the module |
| the `shared` interface and its RPC client/server | bindings generated by `go-in-go bindgen` |
| handshake: protocol version and magic cookie | `Load` checks every export's and import's name and signature against the bindings, and the module's ABI version |
| net/rpc or gRPC call | a function call, ~100 ns, arguments copied |
| the host calls the plugin | exports (`//gig:export`) |
| the plugin calls the host via `GRPCBroker` | imports (`//gig:import`), implemented by the host's `Imports` value |
| version negotiation in the handshake | an export the host calls after loading (`Negotiate` in [`negotiated/`](negotiated/)) |
| gRPC streams | repeated calls: an export per chunk one way, an import per chunk the other |
| plugin logs to stderr, host parses them (hclog) | a `Log` import that goes straight to the host's `slog` logger |
| the plugin opens files itself | the plugin has no operating system and asks the host through imports; the host decides what it may touch |
| plugin crash: the subprocess dies | module panic or crash: the instance dies with `gig.ErrAborted` or a `*gig.FaultError`, and the host keeps running |

## Running each example

The commands below run from the repository root, after `make` (which builds
`./go-in-go`). Like go-plugin's examples, the plugins write their files
(`kv_<key>`, `myfile`) in the current directory.

### basic

```sh
./go-in-go build examples/goplugin/basic/plugin
go run ./examples/goplugin/basic
```

```
time=… level=DEBUG msg="message from plugin" plugin=greeter foo=bar
time=… level=DEBUG msg="message from GreeterHello.Greet" plugin=greeter
Hello!
```

### kv (go-plugin's grpc)

```sh
./go-in-go build examples/goplugin/kv/plugin-plain
./go-in-go build examples/goplugin/kv/plugin-base64

export KV_PLUGIN=examples/goplugin/kv/plugin-plain/kv-plain.gig
go run ./examples/goplugin/kv put hello world
go run ./examples/goplugin/kv get hello
```

```
world

Written from plugin-plain
```

Set `KV_PLUGIN=examples/goplugin/kv/plugin-base64/kv-base64.gig` to switch
implementations: it stores values base64-encoded. go-plugin's `KV_PROTO`
(net/rpc or gRPC) has no equivalent, because there's no transport to choose.
The bindings in `kv/shared/` were generated from `plugin-plain`, and load
`plugin-base64` too because it has the same exports and imports. That's what
makes them a plugin interface.

### bidirectional

```sh
./go-in-go build examples/goplugin/bidirectional/plugin
export COUNTER_PLUGIN=examples/goplugin/bidirectional/plugin/counter.gig
go run ./examples/goplugin/bidirectional put hello 1
go run ./examples/goplugin/bidirectional put hello 1
go run ./examples/goplugin/bidirectional get hello
```

```
2
```

In go-plugin, the host passes an `AddHelper` to each `Put`, and the plugin
calls it through the gRPC broker. Here `Sum` is an import: the host
implements it, and the plugin calls it in the middle of `Put`. Imports
belong to the instance rather than to one call, so to vary the helper per
call, the host changes what its `Imports` value does.

### negotiated

```sh
./go-in-go build examples/goplugin/negotiated/plugin
KV_PROTO=3 go run ./examples/goplugin/negotiated put hello world
KV_PROTO=2 go run ./examples/goplugin/negotiated get hello
```

```
using protocol version 3
using protocol version 2
world

Written from plugin version 3
Read by plugin version 2
```

`KV_PROTO` is the list of versions the host supports. go-plugin's example
uses `netrpc` for version 2 and `grpc` for version 3. The plugin picks the
highest version both sides support: `KV_PROTO=2,3` gets 3. With `KV_PROTO`
unset, the host doesn't negotiate, and the plugin falls back to its oldest
version, 2, as go-plugin does for legacy clients. `KV_PROTO=4` fails with
"no common protocol version".

### streaming

```sh
./go-in-go build examples/goplugin/streaming/plugin
go run ./examples/goplugin/streaming myfile
```

```
{"time":"…","level":"DEBUG","msg":"loading the plugin"}
{"time":"…","level":"DEBUG","msg":"FileStreamer: Write","path":"myfile"}
{"time":"…","level":"DEBUG","msg":"FileStreamer: Write finished"}
{"time":"…","level":"DEBUG","msg":"writing finished"}
{"time":"…","level":"DEBUG","msg":"FileStreamer: Read","path":"myfile"}
{"time":"…","level":"DEBUG","msg":"FileStreamer: Read finished","chunks":"3"}
{"time":"…","level":"DEBUG","msg":"received 26 bytes in 3 chunks","bytes":"Lorem ipsum dolor sit amet"}
```

go-plugin streams to stay under gRPC's message size limit. go-in-go has no
such limit, but chunks still keep memory flat for large data. The host
streams into the plugin by calling the `WriteChunk` export once per chunk.
The plugin streams back by calling the `Send` import once per chunk during
`Read`. Each chunk goes straight to or from the file, so neither side holds
the whole file.

## What doesn't carry over

- **Plugins in other languages.** go-plugin's grpc example includes a Python
  plugin. go-in-go modules are Go, compiled by TinyGo.
- **Process isolation.** A go-plugin plugin can't touch the host's memory. A
  go-in-go module runs in the host's process: panics and crashes are
  contained, but module code using `unsafe` could still corrupt host memory.
  Only load modules you trust.
- **The plugin's own OS access.** A module can't open files or sockets
  itself. Everything goes through imports, as `hostfs/` shows. Whether
  that's a limitation or a feature depends on your plugins.
